# STEP 4D — Evidence-Grounded Reports & Parliamentary Briefing

Status: **STEP 4D — READY FOR MANUAL ACCEPTANCE**

## Existing pipeline audit and root causes

The existing Parliamentary endpoint was a synchronous request. It performed
structured legacy-metric lookup, `execute_rag_query` (which could initialize
ONNX/Chroma or its degraded embedding path), conflict lookup, and narrative
assembly before returning. That made the browser's ordinary 15-second request
budget the effective limit for a multi-stage operation.

The existing PDF endpoint was separate and rendered the client-posted briefing
payload. It did not re-run intelligence, but it also did not require a
persisted completed briefing artifact. The generic report service contained a
hard-coded Rajmahal/OBR fallback when no metrics were supplied, which was not
acceptable for evidence-grounded output.

## Architecture implemented

`app/services/report_grounding_service.py` now provides:

- bounded report specifications;
- structured-fact evidence packets;
- optional semantic evidence retrieval through Step 3 primitives;
- evidence validation states;
- conflict preservation without averaging;
- deterministic narrative fallback and packet fingerprints.

The existing `Report.content_json` field stores the specification, evidence
packet, validation result, deterministic narrative, and fingerprint. No new
database migration was needed.

Generic report generation now uses persisted structured evidence and no longer
inserts fabricated metric rows. Numeric values retain entity, metric, value,
unit, period, validation state, document/page, and table locator where present.

## Parliamentary lifecycle

New authenticated endpoints:

```text
POST /api/v1/parliamentary/briefing/jobs
GET  /api/v1/parliamentary/briefing/jobs/{job_id}
GET  /api/v1/parliamentary/briefing/jobs/{job_id}/export-pdf
```

The POST returns `202 Accepted` promptly and persists a `Report` row with
`report_type=PARLIAMENTARY_BRIEFING`. Duplicate active requests from the same
user with the same specification return the existing job ID. A bounded worker
updates `QUEUED → RETRIEVING → GENERATING → COMPLETED/FAILED`. The existing
synchronous endpoint remains for compatibility and tests. If semantic/RAG
retrieval raises an initialization or provider error, the briefing now
continues in explicit structured-only degraded mode when structured records
exist. It reports the semantic-unavailable warning instead of inventing
context; with no structured or semantic evidence it returns
`INSUFFICIENT_EVIDENCE`.

The frontend Parliamentary page now starts a job, polls without overlapping
requests, displays lifecycle/error state, and exports only the persisted
completed briefing. It does not wait synchronously for the full RAG/briefing
operation.

## Validation and uncertainty

States include:

- `SUPPORTED`
- `SUPPORTED_WITH_WARNINGS`
- `REVIEW_REQUIRED`
- `INSUFFICIENT_EVIDENCE`
- `FAILED`

Step 2C `CANDIDATE/REVIEW_REQUIRED` facts remain visibly unverified. Conflicting
facts remain separate with their source fact IDs. No universal confidence value
is generated by the new grounding layer.

The existing Parliamentary compatibility response now exposes
`validation_state` and `warnings`. Its legacy extracted-metric compatibility
surface is labelled `REVIEW_REQUIRED` rather than presented as canonical
validated evidence.

## PDF/export

Generic reports and Parliamentary PDFs now include validation state, warnings,
numeric evidence status, document/page references, and table row/column
locators where persisted. Missing operands/evidence are rendered as
`Unavailable`. The worker renders and stores the completed Parliamentary PDF
through the existing storage provider. The export endpoint serves that stored
artifact when available, reconstructing the server-persisted response only as
a safe compatibility fallback. Existing PDF content is escaped before
ReportLab rendering.

## Persistence, audit, and RBAC

Existing report history and audit records are preserved. Report generation keeps
Admin/Analyst permissions; approval remains Admin/Reviewer. Generation does not
approve a report. No secrets are written to report metadata.

## Bounded real-data validation

Against `coalintel_step1_acceptance`, an all-period bounded report packet run
loaded 500 structured facts (the service limit), preserved source
document/page/table-cell locators, and returned `REVIEW_REQUIRED` because the
current 10,046 facts are `CANDIDATE/REVIEW_REQUIRED`; conflicts were retained
instead of averaged. No candidate was promoted to authoritative status. The
deterministic PDF renderer produced a non-empty 4,362-byte ReportLab PDF from
the packet. A specifically requested FY 2023-24 packet correctly returned
`INSUFFICIENT_EVIDENCE` because the acceptance sample did not contain matching
period evidence.

The same database contains representative production, dispatch, OBR, and
exploration candidates, but their review-required status prevents unsupported
authoritative calculations. That limitation is intentionally visible for
manual acceptance.

## Manual acceptance procedure

1. Start PostgreSQL, FastAPI, frontend, and the configured Document AI service.
2. Open Parliamentary Briefing and submit the Production Targets preset.
3. Confirm the POST returns promptly and the UI shows `QUEUED`/`RETRIEVING`/
   `GENERATING` rather than timing out.
4. Keep the page open until `COMPLETED` or `FAILED`; verify warnings and
   validation state are visible.
5. Export the completed briefing and verify the PDF contains the report scope,
   validation state, warnings, source pages, and evidence locators.
6. Repeat the same request quickly and verify the active job ID is reused.
7. Generate a generic report and verify no fabricated fallback metrics appear.
8. Verify Admin/Analyst generation and Admin/Reviewer approval boundaries.
