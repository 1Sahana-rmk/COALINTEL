1. Executive Summary
We propose a secure, evidence-grounded AI reporting and knowledge platform for CMPDI/CIL subsidiaries. The platform converts heterogeneous operational records—scanned PDFs, digital PDFs, Word files, spreadsheets, images and historical archives—into searchable structured knowledge, then uses retrieval, validation and controlled generation to answer questions and accelerate report preparation.
The key design principle is not “a chatbot that writes reports.” It is an auditable reporting copilot: every extracted figure and generated statement should retain provenance to the source document, page, table/cell or image region wherever technically possible. The system should distinguish extracted facts from AI-generated narrative and should flag low-confidence or conflicting values for human review.
The prototype should demonstrate three PS-aligned capabilities: (1) automated report generation, (2) topic/word-cloud and trend identification, and (3) an AI query-and-response interface over the organization's documents. The same ingestion layer powers all three.
This approach is realistic for a student prototype because it can be built using mature OCR/document parsers, embeddings, a vector database, PostgreSQL metadata, an LLM API/local model, FastAPI and a React/Next.js interface. We do not need to train a foundation model from scratch.

2. Deep Understanding of the Problem
The PS describes a document-heavy government/enterprise reporting environment. The difficult part is not simply finding text. Important information can be buried in scanned pages, tables, charts, historical documents and spreadsheets. A useful system therefore needs a multimodal document pipeline plus a trustworthy retrieval and reporting layer.
Why the existing workflow is difficult
Repeatedly opening many documents and manually locating relevant figures.
Copying values from tables or scanned documents into working reports.
Reconciling the same metric when it appears in multiple reports or time periods.
Depending on individual staff knowledge to know which archive contains the right evidence.
Slow response to high-priority administrative or parliamentary questions.
Risk of transcription mistakes and inconsistent definitions across years/subsidiaries.
Poor discoverability of historical knowledge because many documents are not semantically searchable.
Difficulty proving exactly where a reported number came from.
Evidence that the document ecosystem is substantial
The Ministry of Coal publicly maintains annual-report archives across many years and also publishes parliamentary-question replies and other transparency records. CMPDI likewise maintains annual reports. This supports the PS premise that a large historical document corpus can be a meaningful input to a reporting/knowledge system. [R1][R2][R3]
The final prototype should not claim access to confidential CIL data. For the hackathon, use public reports, synthetic records, or organizer-provided sample data and explicitly label the demo dataset.

8. AI / ML Technical Approach
A. Document understanding
Scanned documents require OCR; digital PDFs should preserve text and layout where possible. Tables must remain tables rather than being flattened into plain text. Modern Document AI systems explicitly preserve layout, tables and sections because structure improves downstream retrieval and RAG quality. [R4][R5]
B. Chunking
Prefer semantic/section-aware chunks over fixed character windows.
Keep table chunks together with table title, headers, units and source page.
Attach metadata: document, year, subsidiary, document type, page, section and confidence.
Create smaller evidence chunks for precise retrieval and larger context windows for report synthesis.
C. Retrieval
Use hybrid retrieval: exact metadata/keyword filtering + vector similarity. For numeric questions, retrieve candidate evidence and then apply deterministic filters. A reranker can reorder retrieved chunks before generation.
D. Grounded generation
The LLM receives only the selected evidence pack plus a strict response schema. It should be instructed not to invent values. If evidence is missing or conflicting, the answer should say so and surface the conflict.
E. Structured output
For report generation, use a structured intermediate schema such as JSON: report_title, executive_summary, sections[], claims[], tables[], citations[], warnings[]. Structured model output is preferable to asking an LLM to directly produce a final document because the backend can validate the schema before rendering. Structured Outputs are an established approach for constraining model responses to developer-defined schemas. [R10]
Example query pipeline
Question: “What was production for Mine A in FY2024-25, and how did it change from FY2023-24?”
Parse intent: metric=production; entity=Mine A; periods=FY2024-25/FY2023-24; operation=compare.
Retrieve documents using metadata filters and semantic retrieval.
Extract candidate numeric values and units.
Normalize units and verify period/entity match.
Detect conflicts across sources.
Build evidence pack containing values + page citations.
LLM generates a concise comparison only from evidence.
Return answer + citations + confidence/warnings.

10. Topic Identification, Word Cloud & Insights
The PS explicitly requests automated word cloud and topic identification. Implement this as a second analytics view, not as decoration.
Clean OCR text and remove stopwords/domain stop terms.
Extract TF-IDF keywords for interpretable top terms.
Generate topic clusters using embeddings + clustering.
Label clusters using representative keywords or an LLM.
Show year-wise topic frequency to reveal emerging/declining themes.
Link every topic back to source documents so users can inspect evidence.
A useful dashboard can show: top topics, topic trend by year, most referenced entities, recurring issues, document counts, and a click-through list of supporting documents.

22. Research Conclusions
1. The PS is technically credible because the industry already has mature document AI primitives for OCR, layout, table extraction, retrieval and RAG. [R4–R9]
2. A generic “chat with documents” implementation will not be sufficiently differentiated. Major platforms already offer document chat/RAG patterns. The product must add mining-domain structure, validation and report lineage. [R4][R5][R6][R7][R8]
3. Numeric accuracy and provenance are more important for this use case than fluent prose. The architecture should therefore place deterministic validation between retrieval and final report output.
4. GraphRAG is valuable as a future enhancement for cross-document entity relationships, but it should not block the 8-day MVP. Microsoft describes GraphRAG as a structured approach using a knowledge graph and community hierarchy to improve reasoning over private data. [R11]
5. The strongest hackathon story is “from unstructured government documents to auditable decision-ready reports,” not “AI chatbot for coal documents.”

Scanned/digital PDFs, DOCX, XLSX, images, historical archives.
Core engine
OCR/layout + structured extraction + hybrid RAG + validation + LLM.
Core output
Evidence-backed answers, automated report drafts, topic analytics, trends.
Primary USP
Evidence-to-Report automation with numeric validation and report lineage.
Trust principle
AI drafts; evidence + deterministic checks + human review govern official output.
MVP
Upload → process → search → cited answer → generate report → review → export.
PPT architecture
Data Sources → Document AI → Knowledge Layer → AI Reasoning → Trust Layer → Outputs.
8-day success condition
One polished vertical slice that works end-to-end on a curated public/demo corpus.
